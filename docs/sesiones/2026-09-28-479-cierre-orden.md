# 2026-09-28 — La orden cerrada conserva su foto aunque vuelva a abrirse

## Qué se hizo

- Se bloquea el cierre si quedan partes de horas, costos o facturas, contingencias o cambios de presupuesto pendientes, indicando tipo e identificador de cada carga.
- Cada cierre congela nueve bloques económicos en una foto append-only, versionada y aislada por RLS.
- La reapertura exige motivo, actor y fecha; agrega una versión enlazada sin borrar la anterior y deja la orden lista para incorporar datos tardíos.
- Se agregaron las rutas de cierre, reapertura e historial al contrato OpenAPI y se cubrieron permisos, errores HTTP, migración y RLS real.
- Prompt vigente usado: `b3e7221`.

## Decisiones que tomé sobre la marcha

- **Qué decidí:** la reapertura crea inmediatamente una nueva versión con el motivo y conserva el congelado previo; el cierre posterior crea otra foto con los hechos nuevos. **Qué otra opción había:** guardar el motivo fuera de la foto hasta el cierre siguiente. **Por qué elegí esta:** el issue dice que reabrir genera una foto nueva y el historial queda completo incluso si la orden nunca vuelve a cerrarse; aplica Constitución §9 sin inventar un campo transitorio no pedido.
- **Qué decidí:** los pendientes bloqueantes son los estados pendientes que hoy existen en el modelo: partes `CARGADO`, costos/contingencias `PENDIENTE` y presupuestos `BORRADOR` o `PREPARADO`. **Qué otra opción había:** agregar estados nuevos a inventario y asignaciones. **Por qué elegí esta:** ampliar esos modelos era otro alcance y una migración de dominio no especificada; se respetó Constitución §9.
- **Qué decidí:** la inmutabilidad se protege también en PostgreSQL con un trigger que rechaza `UPDATE` y `DELETE`. **Qué otra opción había:** confiar sólo en que el servicio no expone mutaciones. **Por qué elegí esta:** DOM-01 exige append-only y la base es la última barrera.
- **Qué decidí:** reutilizar el informe de desvío vigente para congelar costos, márgenes, partidas y causas. **Qué otra opción había:** duplicar las fórmulas en el cierre. **Por qué elegí esta:** evita dos fuentes de verdad y respeta la prohibición de reescribir el motor.

## Dónde el issue no alcanzaba

- No define un estado pendiente para movimientos de inventario ni para aplicaciones de pools. Esos registros se consideran hechos confirmados porque el modelo vigente no ofrece otra distinción.
- No define si la foto generada al reabrir debe incorporar hechos nuevos. Se conservó exactamente la foto anterior con el motivo; los hechos tardíos aparecen en la foto del cierre posterior.
- La base local compartida tenía una migración fallida previa (`20260925222000_add_inventario_devoluciones_transferencias`). Para no modificar ese estado ajeno, la suite se ejecutó en un contenedor PostgreSQL desechable y limpio, con rol de aplicación sin `BYPASSRLS`.
- La primera corrida HTTP y la primera corrida unitaria completa tuvieron timeouts de arranque en tests preexistentes; ambos pasaron en la corrida completa posterior con el entorno configurado.

## Qué quedó afuera

- La pantalla frontend, expresamente fuera de alcance.
- Estados nuevos de validación para consumos o asignaciones; no se abrió un issue nuevo porque el pedido no define su circuito de aprobación.
